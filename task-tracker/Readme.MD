# Task Tracker CLI

A simple command-line tool to track and manage your to-do list, built with plain TypeScript and Node.js — no external CLI frameworks (no `commander`, `yargs`, etc.) and no database. Arguments are parsed straight from `process.argv`, and tasks are persisted to a local `tasks.json` file using the native `fs` module.

This project follows the spec at [roadmap.sh/projects/task-tracker](https://roadmap.sh/projects/task-tracker).

## Features

- Add, update, and delete tasks
- Mark a task as `in-progress` or `done`
- List all tasks
- List tasks filtered by status: `done`, `todo`, `in-progress`
- Tasks are stored in `tasks.json` in the current working directory, created automatically on first run

## Requirements

- [Node.js](https://nodejs.org/) (v16+ recommended)
- npm

## Installation

```bash
git clone <this-repo-url>
cd task-tracker-cli
npm install
```

The only dependency is `typescript` itself, used as a dev dependency to compile the source — no runtime libraries are used.

## Build

```bash
npm run build
```

This compiles `src/*.ts` to `dist/*.js` and marks `dist/index.js` as executable.

## Running

You can run it two ways:

**Directly with Node:**

```bash
node dist/index.js <command> [arguments]
```

**As a linked global command** (optional, for convenience):

```bash
npm link
task-cli <command> [arguments]
```

`npm link` creates a global symlink so `task-cli` becomes available as a shell command on your machine. Undo it later with `npm unlink -g task-cli`.

The examples below use `task-cli`; substitute `node dist/index.js` if you haven't linked it.

## Usage

### Add a task

```bash
task-cli add "Buy groceries"
# Task added successfully (ID: 1)
```

### Update a task

```bash
task-cli update 1 "Buy groceries and cook dinner"
# Task updated successfully (ID: 1)
```

### Delete a task

```bash
task-cli delete 1
# Task deleted successfully (ID: 1)
```

### Mark a task as in progress or done

```bash
task-cli mark-in-progress 1
# Task marked as in-progress (ID: 1)

task-cli mark-done 1
# Task marked as done (ID: 1)
```

### List tasks

```bash
task-cli list              # all tasks
task-cli list done         # only completed tasks
task-cli list todo         # only not-started tasks
task-cli list in-progress  # only in-progress tasks
```

## Task properties

Each task stored in `tasks.json` has the following shape:

| Property      | Type                                    | Description                          |
|---------------|------------------------------------------|---------------------------------------|
| `id`          | `number`                                 | Unique identifier, auto-incremented   |
| `description` | `string`                                 | What the task is                      |
| `status`      | `"todo" \| "in-progress" \| "done"`      | Current state of the task             |
| `createdAt`   | `string` (ISO 8601)                      | When the task was created             |
| `updatedAt`   | `string` (ISO 8601)                      | When the task was last modified       |

Example `tasks.json`:

```json
[
  {
    "id": 1,
    "description": "Buy groceries",
    "status": "todo",
    "createdAt": "2026-07-24T10:15:30.123Z",
    "updatedAt": "2026-07-24T10:15:30.123Z"
  }
]
```

## Error handling

- Missing required arguments (e.g. `add` with no description) print a usage message instead of failing silently.
- Non-numeric task IDs are rejected with a clear message.
- Referencing a task ID that doesn't exist reports "Task not found" rather than crashing.
- An invalid `list` filter (anything other than `done`, `todo`, or `in-progress`) is rejected with the valid options listed.
- A corrupted or hand-edited `tasks.json` that fails to parse produces a clean error message instead of a raw stack trace.
- Running with no command, or an unrecognized one, prints full usage instructions.

## Design notes

- **No CLI parsing library.** Arguments are read directly from `process.argv.slice(2)`; the first element is treated as the command, the rest as its arguments.
- **No database.** `tasks.json` is read and rewritten in full on every write operation (`fs.readFileSync` / `fs.writeFileSync`), which is simple and sufficient for a single-user local CLI tool.
- **IDs** are computed as `max(existing ids) + 1`, so deleting a task never causes a later `add` to reuse a freed-up ID.
